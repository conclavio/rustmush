## G.1a

The first half of G.1, split by the lead on 2026-10-22: the mining session's uncommitted SM.10 is editing `mush-config/src/config.rs`, `tests/shipped_configs.rs`, `mushd.toml.example` and the deploy template, exactly where `[pixel]` goes, so everything that needs no config lands now and G.1b (the step-down, `[pixel]`, `@pixel/stats`, the `u` key's gate) follows SM.10's commit.

**What landed.**

- **The picture seam** (`mush_pixel::picture`, D-21-7): `trait Picture { feeds, interval, draw(frame, &dyn Feeds, &Look) -> bool }`, `trait Feeds` (a held keyframe by feed name; implemented for the TUI's `PanelStore` and for `HashMap<String, Value>`), `Look` (the viewer's local heading offset, D-21-14), and the two bucket clocks `BUCKET_A_INTERVAL` 50 ms and `BUCKET_B_INTERVAL` 200 ms. The cockpit is the first picture: `mush_pixel::cockpit::CockpitPicture` owns the map cache (rebuilt when the held `arena.map`'s match changes, open ground of 512 cells while none is held), the camera from the frame plus the look, the sprites and the instruments. The TUI's `PixelView` keeps only the probe, the keys, the clock, the change test and the placement; its `paint` takes the panel store as `&dyn Feeds`, so G.3's socket frame and G.3b's WebAssembly render drive the same type.
- **`map_from_feed` moved into the engine**, a self-contained decoder of `arena.map`'s run-length rows with `mush_ansi::window_rows`' rules (a run with no length is one cell, a run past the width is clipped, a malformed run skipped, a short or missing row is spaces), so `mush-pixel` still depends on nothing but `flate2` and `serde_json` (the WebAssembly constraint of §4.3). The fixture example lost its third copy of the decoder and drives `CockpitPicture` through a `HashMap` of feeds.
- **The two-pass raycaster** (`raycast::render`). The rays are still cast a column at a time, but a column now leaves only where its sky ends, its wall slice and where its floor starts; the frame is then written row by row along memory, the sky band and the floor's distance and fog step worked out once a row, and every colour read from a table built once a render (16 bases × 12 fog steps, 16 sky bands) instead of three float lerps a pixel. The expressions are the spike's term for term, so the result is **the same pixels**: `the_two_pass_render_matches_the_spike_pixel_for_pixel` keeps the spike's renderer under `#[cfg(test)]` and compares 48 headings × 3 frame sizes × 2 maps (a walled yard, 512 cells of open ground) with sprites, and the fixture PNG is byte-identical before and after (6,967 bytes).
- **A bug the reference found**: under a ray that hits nothing within 160 cells, the spike drew no pixel on the horizon row, so that row kept whatever the frame last held (black from `Frame::new`, or a sprite from an earlier frame, which could leave a trail along the horizon of an open view). Every pixel is drawn now, the gap in the horizon colour, which was already in the palette; `every_pixel_is_drawn_whatever_the_frame_held` pins it.
- **`Frame::hash` eight bytes at a time** (FNV's offset and prime with a rotate). The frame clock hashes every tick whether it sends or not; the byte-at-a-time FNV read 921,600 bytes a tick at 640x480. The value is only compared within a connection, so its change is free.
- **The probe's attribute set** (`mush_pixel::caps`). `Key::DeviceAttributes` carries the DA1 reply's `DeviceAttributes` (level and the attributes below 64); the probe ends in `Probe::Done` with a `Graphics { kitty, sixel }` record, sixel read off attribute 4 whichever answer came first (a kitty OK then DA1, as WezTerm and w11term answer, still records sixel). `Graphics::encoder()` is D-21-5's choice and yields `Kitty` alone until G.2 adds sixel; the view opens only on an encoder. The HUD's probe words are now `kitty graphics OK`, `sixel only (not drawn yet)` and `no terminal graphics`.
- **The help G.0 owed**: `help cockpit` gains "The picture" (the keys, that a look is not a turn, the terminals that show it — w11term first, WezTerm's own SSH client with the software front end, kitty and Ghostty — and the ones that do not yet, Windows Terminal and the sixel terminals; ConPTY's loss of the picture; tmux unsupported; what the probe line says), and `help tui`'s keys gain `Ctrl-G`.
- **Amendments made**: doc 02 §5.6 gains the graphics capability bullet; doc 16 §11 records the picture as §5's fourth surface; doc 21 Draft 0.5 records the split.

**Measured** (the fixture scene, 640x480, release, the owner's box, 200 draws averaged): render plus instruments **4,024 µs before, 945–974 µs after** (4.2×); PNG encode unchanged at ~1.2 ms, now the larger half of a frame's cost; 57 colours; PNG 6,967 bytes, kitty stream 9,382 bytes. On the spike's ratio (the VPS read 7.6–8.6 ms where this box read about 4) the VPS should land near 2 ms, well under G.1's ≤4 ms acceptance; the VPS figure itself is owed to G.1b's dev2 smoke (no deploy without the owner).

**Not in G.1a, for G.1b.** The step-down on back-pressure, first establishing what russh does with a client that stops reading (whether `Handle::data` blocks the pump until `WRITE_TIMEOUT` or buffers inside russh); `[pixel]` in `mushd.toml`; `@pixel/stats` intercepted in the gateway and the box counters in the gateway's `Metrics`, the HUD's engineering numbers moving there; the `u` key's gate (the gateway does not know who is staff: a box-wide `[pixel] diagnostics` switch, or a staff bit on `SessionInfo`, is the owner's call). Also left: the PNG encode (its colour count is a `HashSet` a pixel) is the next millisecond to take if a frame's cost matters again.

**Verified.** `cargo test -p mush-pixel` (25), `cargo test -p mush-net-ssh` (all suites), `cargo test -p mush-contract-tests --test help_commands`; clippy with the crate's restriction lints, rustfmt and rustdoc `-D warnings` over the two crates. Not smoked in a terminal: the TUI path is unchanged but for where the picture comes from, and the bytes it sends are pinned by the existing `the_probe_reply_opens_the_pixel_view_and_paint_carries_a_kitty_frame`.

## G.2

Sixel, started while the mining session's SM.10 holds `mush-config` (G.1b waits for it); G.2 needs no config.

**What landed.**

- **The encoder** (`mush_pixel::sixel`): `DCS 0;1;0 q`, raster attributes `"1;1;W;H`, one `#i;2;r;g;b` register a colour the frame uses (percent), six-row bands with a line a colour present in the band (`$` between, `-` after), runs of four or more as `!n`, each line stopped at its last set column, `ST`. One pass a band builds every colour's line at once. A frame past 256 colours is cut to 3-3-2 first (no producer draws one). `sixel::fit` sizes a frame to a pixel box at the wanted aspect; `sixel::frame_bytes` wraps it in synchronized output with the cursor move.
- **Verified by a decoder, not a reference encoder.** The acceptance asked for a byte compare against a reference encoder; there is none in the tree and no `libsixel` on the box, so the tests carry a decoder for the encoder's subset and demand the cockpit fixture (at 640x480, 320x220 and 333x250) and edge frames (one pixel, heights that are and are not multiples of six) decode back to their pixels through sixel's percent precision; a five-by-seven frame's bytes are pinned. The MW2 frame is not in the tree and was not re-run.
- **Shown in Windows Terminal.** The fixture's `fixture.sixel` (the example now writes one) typed through `cmd` in Windows Terminal 1.24 stable — through ConPTY, the path `ssh.exe` takes — draws the cockpit with every instrument. It also showed WT scaling sixel pixels to its own cell (a 640-pixel frame filled about 900 screen pixels), which is why the box is sized from the terminal's reported cell rather than its real pixels.
- **The cell size.** The probe (`caps::probe_bytes`, which now owns the whole sequence; `kitty::query_bytes` is the kitty half) sends `CSI 16 t` between the kitty query and DA1; `Key::CellSize` carries a `CSI 6 ; h ; w t` reply, any other `CSI … t` is swallowed. A terminal that does not answer is taken to have a 10 by 20 cell, the VT340's and Windows Terminal's virtual one. The SSH `pty-req` pixel size is still not read: it is a real-pixel size, which is the wrong unit for WT. **Not verified: whether Windows Terminal answers `CSI 16 t`** (the default covers it if it does not).
- **The box.** `sixel_box`: the wanted frame (640x480, or `r`'s 320x220), or the largest of its aspect that fits the rows between the HUD lines in cell pixels, placed at row 2 column 1, its cell box the frame rounded up to whole cells so the picture never reaches the legend and the terminal never scrolls under it. At 120x40 with 10x20 cells the full frame takes 64 by 24 cells; at 80x20 it shrinks to 480x360.
- **The encoder choice** (D-21-5): `Graphics::encoder` is kitty, then sixel, then none; `EncoderChoice` (`auto`, a forced encoder, `off`) sits over it, and a forced encoder does not wait for the probe.
- **A sixel picture lives in the cell grid**, so: the SSH backend watches its cell box and reports any text drawn into it or a screen clear (`SshBackend::set_watch`, `take_touched`); an event or key repaint that touched it makes the next tick send the picture again (`PixelView::text_touched`), while a kitty image is above the text and never resent for it; a picture whose box moved or shrank goes out under a full text repaint (`take_wipe`); and closing the view repaints the whole text frame over it instead of sending kitty's delete. Leaving the TUI needs nothing: the alternate screen goes with it.
- **The rate: 20 Hz, the owner's ruling during the cut.** Measured on the fixture (release, the owner's box): sixel encode 1.11 ms (PNG 1.12 ms); the sixel stream 20,631 bytes raw against kitty's 9,382, and after zlib at level 6 6,594 against 6,680. D-21-16's 10 Hz assumed a frame twice kitty's; the owner: keep it at 20 Hz when it compresses the same. **The caveat, recorded:** russh is built with `flate2`, so the gateway offers zlib, but the client chooses and OpenSSH's (`ssh.exe` included) defaults to `Compression no`; without `ssh -C` a sixel viewer is about 410 KB/s at 20 Hz against kitty's 190 KB/s. `help cockpit` recommends `ssh -C`; G.1b's step-down is the guard for a slow link.
- **`@pixel/encoder [auto|kitty|sixel|off]`**, per connection (the owner: account persistence later; D-21-17 says per account). Read by the SSH front end like `@history`, in line mode and at the TUI's input line, never the world's; kept on the connection so it survives `@notui`; a change closes an open picture. Bare, it says what is set, what the probe found and what `Ctrl-G` draws in. An allowlist row covers `@pixel` in the help test.
- **The HUD** says `sixel graphics OK, drawing sixel` (or `kitty`, `(forced)`), the clock from the picture's interval, and `image` bytes for either encoder (the `Stats` field `png_bytes` is now `image_bytes`).
- **Help**: `help cockpit` "The picture" lists which terminals get which encoder (Windows Terminal through `ssh` gets sixel), recommends `ssh -C`, and documents `@pixel/encoder`. Doc 02 §5.6 amended; doc 21 Draft 0.6 with D-21-3 amended.

## G.2b

Sixel fills its box. The owner, on the smoke's finding that a sixel picture is drawn at its own pixel size: "if we want to support sixel, we're going to have to render the frames larger to fill the space … the tiny little box in the corner won't work".

**The lead's choice: scale in the encoder, not a larger render.** A kitty terminal does not get a larger frame either — it stretches the 640x480 PNG over the cell box. So the sixel picture is the same frame, rendered at the same size, and `sixel::encode_scaled(frame, out_w, out_h)` writes it nearest-neighbour at the box's size: output pixel (`x`, `y`) is source pixel (`x·w/out_w`, `y·h/out_h`). The encoder works at the source width — each source column carries the count of output columns it covers, so a wider picture only lengthens runs `!n` already writes in a few bytes — and maps each output row to its source row, so its time and bytes grow with the rows shown, not the area. Rendering larger was the alternative: a sharper picture at a render cost growing with the area (7× at 1717x1288), and the instruments' 5x7 font would need a scale per size.

- `sixel::fill(frame, avail, max_scale)`: the largest size of the frame's aspect inside the box, at most `max_scale` times the frame. `SIXEL_MAX_SCALE` is 3 (1920x1440 at most; for `[pixel]` in G.1b).
- `sixel_box` now returns the render size, the shown size and the cell box: the frame renders at `want` when the box is larger and at the shown size when it is smaller (a small terminal still gets the instruments' text drawn at the size it is seen, as G.2 did); the box is the shown size in whole cells.
- The sent-picture key carries the shown size, so a cell-size answer that changes it resends; the HUD prints `640x480 shown 1013x760` when they differ. `Pixels`, `CellBox` and `SentKey` name the view's tuples.
- `encode` is `encode_scaled` at the frame's own size, byte for byte (the pinned five-by-seven frame unchanged).

**Measured** (the fixture, release, the owner's box; render unchanged at ~0.95 ms):

| shown | encode | raw | after zlib |
|---|---|---|---|
| 640x480 (G.2) | 1.28 ms | 20,631 B | 6,594 B |
| 1013x760 (Windows Terminal, 120x40, its 10x20 virtual cell) | 2.02 ms | 31,294 B | 9,614 B |
| 1717x1288 (w11term, 240x48 high-DPI, 15x28 cells) | 2.85 ms | 47,050 B | 12,091 B |

At 20 Hz the largest is ~940 KB/s raw and ~240 KB/s compressed: `ssh -C` matters more for a big sixel box, and G.1b's step-down is its guard.

## G.4

The camera on a leash (D-21-14), taken while SM.10 holds `mush-config` and the web client's files (G.1b and G.3 both wait on it). The owner's three defaults (2026-10-22): the arrows turn the tank, `,` and `.` look, hold-to-turn where the keyboard protocol allows, the turn rate measured from frames.

**What landed.**

- **`tui::helm::Helm`**, pure and clocked by the caller. A turn is a **helm order**: a `HEADING <deg>` line sent to the world as if typed, so the sim's own rules decide it (the helm channel, power online, the per-unit order rate). Starting a turn orders the predicted heading plus a lead of a pulse and a half of turning (20°–120°); while it is held, the order is extended when the prediction comes within half a lead of it (at most every 250 ms); stopping orders the predicted heading, so the tank stops about where the picture showed it. The pulse is read from the frame's `tempo` word at the shipped `[tacsim.arena.tempo]` defaults (quiet 5000, alert 1000, engaged 500 ms).
- **Prediction (the interpolation)**: the last frame's heading, carried toward the order at the turn rate from the later of the frame's arrival and the order's sending, for at most a pulse and a half, never past the order. An order no frame has answered a second past its pulse is taken as refused (no helm, no power) and the frame's heading stands — the picture never claims a turn the sim has not made for longer than that. Each frame (a new `t_ms`) is the truth and resets the base.
- **The turn rate is measured**: no client feed carries `turn_rate_mdeg_s` (it lives in the unit definition's mobility mode), and adding it is a `tacsim` change the mining train has asked us to stay out of. The helm starts at the stock tank's 30°/s and takes the rate from two consecutive frames whenever the tank was still short of the order at the second (a turn that finished mid-pulse would read slow). The owner asked whether the rate should depend on speed and tonnage: today the sim's is static per mobility mode; a speed curve per chassis is the suggested shape, a `tacsim` design for after the train, and the helm's measurement follows whatever the sim does.
- **The keys** (`PixelView::key`, which now takes the time): Left/Right turn the tank — held where the view pushed the kitty keyboard protocol, toggled elsewhere; `a`/`d` turn it toggled; `,`/`.` swing the **look** (the old 45°/s camera offset, ordering nothing); `c` recentres the look; space stops both. A seat without the helm turns nothing and keeps the look.
- **The kitty keyboard protocol**: the `@tui` probe asks `CSI ? u` (before DA1); a `CSI ? flags u` reply (`Key::KeyboardFlags`) marks the terminal; opening the view pushes `CSI > 3 u` (disambiguate, report event types) and closing or leaving the TUI pops it (`CSI < u`), so the rest of the TUI reads keys as before. The parser gained the protocol's forms: a cursor key's repeat and release (`Key::Repeat`, `Key::Release` with `Arrow`), every other key's release swallowed, and the `CSI <code>;<mods> u` form of Esc, Enter, Tab, Backspace and the Ctrl and Alt chords — so Esc still closes the view and `^]` still detaches with the protocol pushed.
- **Plumbing**: the view's orders reach the world by the TUI's ordinary submit path (a key's start or stop) and by the output pump after a frame tick (a held turn's extension; a view that just closed); leaving the TUI with a turn in progress stops it and sends the order before the TUI is dropped.
- **The HUD** reads `camera 120° (tank 090° → 135°, look +30°)  turning right`; the legend says whether the arrows are held or toggled. `help cockpit` documents the keys, that a turn is an order, and the `Steering to …` replies.

**Smoked live on dev2 (2026-10-22, at `8e01dd93`).** The gateway alone rebuilt (3 m 30 s), and the restart was clean (`the server exited cleanly`, the fix of `29b0ecd4` at work). `pixeltest` on a range in w11term at 240x48: w11term **answered `CSI ? u`**, so the view pushed the protocol and the legend read `←/→: turn the tank (hold)`. A held → (its press, then four seconds later its `CSI 1;1:3 C` release, sent through w11term's control pipe) turned the tank **090° → 247° in 4.2 s**, about 38°/s against the 30°/s assumed (measured from frames), with the camera within 2–5° of the tank all the way; the order was extended three times (`Steering to 210°.`, `272°.`, `333°.`, one a second) and the release ordered `257°`, where the tank stopped and stayed — no overshoot, the picture and the frame agreeing (`HDG 257` in the strip). The HUD kept `→ 257°` until the confirming frame a slow pulse later; it now hides an order the picture shows reached.

**Not done, recorded.** The cockpit frame does not carry the ordered heading or the turn rate; carrying both would let a second connection draw the same prediction and remove the measurement, a small `tacsim` change for after the mining train. A disconnect mid-turn leaves the last order standing (the tank finishes at most a lead of turn). Doc 17's §6, which doc 21 §14 names for this amendment, is the scheduling section; the amendment is held for the owner to place.

**Verified.** `tui::helm` (six tests: short arcs, no frame no order, the lead and the release, the measured rate only short of the order, an unanswered order let go a second past its pulse, a held turn extended before it runs out); the view (the look orders nothing; toggled and held arrows, repeat and another key's release ignored, the push and pop bytes); the parser (the flags reply, an arrow's press, repeat and release, Esc and `^]` and `^G` in the `CSI u` form, a Delete release swallowed); `mush-net-ssh` every suite; clippy, rustfmt, rustdoc.

## G.3a

The gateway half of G.3, taken while SM.10 holds the web client's files (`web/src/lib/game.svelte.ts`, `stores/screens.svelte.ts` and others in its uncommitted diff); the canvas in the cockpit tab is **G.3c**, after SM.10 lands (G.3b stays the WebAssembly render).

**What landed.**

- **`ClientCommand::Picture { on, look_mdeg }`** (`mush-proto`, additive; the TypeScript binding regenerated, `web/src/lib/proto/ClientCommand.ts` the only web file touched): the web client asks for the picture, changes its look (the camera's offset; turning the tank is a `HEADING` line), or stops it. Transport-local: the web pump answers it and the world never sees it.
- **`mush_net_web::picture::WebPicture`**, one a connection, in the socket's pump (`ws.rs`): every envelope bound for the socket passes `observe` on its way out, which keeps the latest `arena.cockpit` and `arena.map` **keyframes** (pushed or in a query's `Reply`), so the picture shows what this connection's own stream carries (D-21-1); a delta is ignored (these two feeds send keyframes; the client asks for one on a delta, and it passes through the same pump), and a cockpit keyframe with `seated: false` drops the held one.

A send that misses the socket's `send_timeout_ms` closes the connection as slow, as an envelope's would (G.1b's step-down will soften both).
- **No feature flag in `hello`**: the web client ships embedded in the same gateway binary, so the two always match; the hello's feature list stays the server's.
- Doc 02 §6.3 records the binary frames.

**What the survey found.** Heights exist upstream and the sim uses them: the proving ground's atlas region imports a heightfield (four 128x128 `le16` tiles at 10 m, doc 14 §3.5), the arena sets each unit's `z_cm` from its cell, charges climbs and refuses steep edges, and line of sight follows the ground (doc 16 §11, cut X.6). **What landed.**

- **`mush_pixel::heightfield`**: `Terrain` (the arena's `Map` plus an elevation a cell, kept also as heights in cells and a light flag a cell, both updated as heights are set) and `render(frame, terrain, camera, eye_cm, sprites)`. Heights interpolate between cell centres (a step becomes a one-cell ramp); walls stand `WALL_H` (8 m) and woods `WOODS_H` (6 m) above their cells as flat-topped blocks; each cell is lit or shaded by its slope toward a north-west sun (two levels, from its four neighbours); the eye stands 2.5 m above `eye_cm` (the frame's `z_cm`) or the ground under the camera; units stand on the ground at their own point and a per-pixel depth lets a ridge hide part of one. - **The proving ground in the tests**: `tests/support/atlas.rs` decodes the shipped pack (`crates/tacsim/content/atlas/proving_ground.json`: the base64 `le16` samples with `scale_cm` and `datum_cm`, the run-length class codes mapped to the raycaster's ground) into a `Terrain`, read-only — `mush-pixel` gains no dependency on `mush-atlas`, and the engine will be handed heights by a feed, not by the content pack. ### G.7a addendum: the baked colour map

The owner, reading Voxel Space (s-macke): would a colour map make sense for our maps? The renderer already was Voxel Space's algorithm; its other half, the **colour map**, is now `Terrain::bake(seed)`. Agreed constraints: baked from what the viewer's feed carries (heights and classes), never from content the feed does not carry — on Ceres the geology key must not paint its deposits (D-21-1); heights stay at the sim's resolution (only colour is finer); a small palette, judged on frame bytes.

- **Two levels**: a fine map of 2.5 m texels (four to a cell side) for ground nearer than 8 cells, and a coarse one (a texel a cell) beyond — at distance the fine texels aliased, a light level's edge shimmering into dashes across neighbouring columns (the first try); the coarse level removed it.
- **The light**: the normal of the interpolated surface (its relief exaggerated four times, so metre terraces read) against a north-west sun 45° up, **minus a steepness term** (any steep slope darkens, whichever way it faces — the fix for slopes facing across the sun, which a pure directional light leaves flat), minus a little in hollows (a cell below its 5×5 neighbourhood's mean), plus a soft seeded mottle in blobs of two to five cells; quantized to 4 levels × 6 ground kinds × 6 fog steps (144 colours at most, a frame using a few dozen).
- **Cost and bytes** (640x480, release, the owner's box; render times swing ±10 % with the box's load):

| scene | | render | colours | PNG |
|---|---|---|---|---|
| proving ground, middle, looking north | per-cell light | 2.50–2.86 ms | 41 | 1,932 B |
| | baked | 2.65–3.00 ms (+5 %) | 41 | 3,053 B |
| crater 240 m × 30 m, from its floor | per-cell light | — | 25 | 3,670 B |
| | baked | — | 26 | 4,096 B |
| (the raycaster's cockpit, for scale) | | 0.95 ms | 57 | 6,967 B |

  The bake is 33–42 ms once a map (65,536 cells → 1,048,576 fine texels + the coarse map). The baked crater reads as a crater (its near wall in shadow, its far wall lit, its floor modelled) where the per-cell light drew flat bands split by a jagged cell edge; on the terraced proving ground it shows the terraces as bands.
- **Not decided here**: whether the cockpit uses the bake by default (G.7b, with the reworked arena), the sun's direction and the gains, and where a bake runs (once per map in the gateway, shareable across a match's viewers, or in the browser at G.3b).

## G.1b

The second half of G.1, after SM.10 landed its config edits (fed09da2): the step-down, `[pixel]`, `@pixel/stats`, the `u` key's gate, the box counters.

**What russh does with a client that stops reading** (the question G.1a left). `Handle::data` only queues a message to the session task (russh 0.63.1, `server/session.rs`); the session task sends what the channel's window allows and keeps the rest pending — and while any channel has pending data it **stops taking from the handle's queue** (`msg = self.receiver.recv(), if !self.kex.active() && !self.common.has_any_pending_data()`). So once the client's window is full, the queue fills and the next `Handle::data` waits. A picture write that waits is therefore the back-pressure signal, and nothing piles up without bound inside russh; a client that stops reading entirely still meets the pump's 5 s write timeout and is closed, as before.

**What landed.**

- **The step-down** (`PixelView::write_took`, doc 21 §3.4): the output pump times each write that carries a picture; one slower than a frame (the view's current interval) skips the next tick's picture (`Stats::slow_skips`); `step_down_after` of them in a row step the view down — the frame to 320 wide (`FRAME_W_LO`, at the picture box's shape) and the clock to `low_interval` — and `step_up_after` of writes that keep up step it back. The status line says `slow link: stepped down`; `StepChange` tells the pump what happened for the counters.
- **`[pixel]`** (`mush_config::config::PixelCfg`, `deny_unknown_fields`, every key defaulting): `frame_interval_ms` 50, `low_interval_ms` 100, `step_down_after` 3, `step_up_after_s` 10, `diagnostics` false. The gateway's SSH bridge takes it (`SshBridge::with_pixel`, in the split gateway and the all-in-one `mushd`) and hands it to each `@tui` through a new `SshHooks::pixel_config` (default: the built-in values), as `mush_net_ssh::PixelConfig::from_millis`, which holds the numbers to sane bounds. `mushd.toml.example` documents the block; the deploy template declares it with `diagnostics = __PIXEL_DIAGNOSTICS__` — `false` in the example instance and dev1, `true` on dev2, the smoke box.
- **The `u` gate**: `u` works only with `diagnostics` on, and only then does the legend offer it and the status line carry the engineering numbers (render, encode, image, wire, sent, fps). Turning diagnostics off drops an uncapped clock.
- **`@pixel/stats`**, read transport-side like `@pixel/encoder`: inside `@tui`, three lines into the scrollback — what the terminal showed and what is drawn, open or closed; the frame, the clock, stepped down or not, the last frame's render and encode times and bytes, the frames of the last second; sent, unchanged, skipped on a slow link, stepped down. Outside `@tui` it says the numbers are told there.
- **The box counters**: a new `SshHooks::pixel_event` (default: ignored) carries `Opened`/`Closed` (the pump compares "viewing" before and after each wake, and closes it at teardown, so the gauge cannot leak), `Sent(bytes)`, `SlowSkip` and `SteppedDown`; the gateway's bridge turns them into `Metrics::pixel_*` and `/metrics` serves `mush_pixel_viewers`, `mush_pixel_frames_total`, `mush_pixel_bytes_total`, `mush_pixel_slow_skips_total`, `mush_pixel_step_downs_total`. `healthz` is unchanged (it stays four lock-free scalars).
- **Docs**: `docs/ops.md` gains "The terminal picture: `[pixel]`"; `help cockpit` the slow-link paragraph and `@pixel/stats`.

**Verified.** `mush-net-ssh` (the step-down end to end on the view: one slow write skips one frame, three step down to the narrow frame at 10 Hz, nine clean seconds do not step up and ten do; `u` inert without diagnostics and the numbers off the status line; `@pixel/stats` parsing; the bounds), `mush-config` (the shipped-config census and parity tests with the new block and placeholder; the Prometheus text), `mush-gateway` and `mushd` build, clippy, rustdoc. **Not measured live**: the VPS render figure G.1 owes and a real slow link are for the next dev2 smoke.

## G.5a

The scene model (§3.3, D-21-8), the first half of G.5 (the owner's plan of 2026-10-22: G.5a the scene and the minimap, G.5b the chart picture in the TUI, G.5c the web chart's light-lag rings).

- **`mush_pixel::scene`**: a `Scene` is a `Viewport` — a world rectangle (y up) on a frame rectangle (y down) through a `Transform`, `Linear` or the orbital view's `LogRadial { r0, r_max }` (`ln(1 + r/r0) / ln(1 + r_max/r0)` of 0.94 of the half-side, clamped, at the point's own angle: doc 19's chart scale, as the web's SVG draws it) — and `Layer`s of `Item`s drawn in order:
  - in the world, through the transform: `Rect`, `Line`, `Polyline`, `Trail` (per-point ages, a segment past `old_after` in its old colour), `Circle`, `Arc` (an arc or a filled sector, bearings clockwise from north). A curve the transform bends is sampled: a circle in 180 pieces, a straight line cut into pieces no longer than 6 px on the page;
  - at a world point, sized in pixels: `Marker` (square, disc, ring), `Ray` (a bearing and a length), `Text` (the 5x7 font, an offset, top-left or centred);
  - frame rectangles: `Panel` (a fill and a border), `Image` (an embedded `Frame`).

  Dashes are by pixel count along the stroke. No blending, no anti-aliasing: the overlay's Bresenham, fills and font (now `pub(crate)` in `overlay`) are the rasteriser's, so a scene keeps the frame inside the PNG's 256 by its builder's colours.
- **The minimap is a scene** (`overlay::minimap_scene`; `draw_minimap` draws it): panel, 3,600 cell rects, spot letters, contact squares, the pilot's ray and square. **G.5's acceptance, pixel-equal before and after**: the old drawer is kept under `#[cfg(test)]` and the two are compared over 96 cases — three frame sizes (both scales and the text cockpit's 640x256), four positions including the map's corner and far edge (cells off the map), eight headings — and are the same pixels every time.

## G.10

Bells and sounds, in the TUI. Rulings taken here (each cheap to unwind):

- **The sound names are the notice kinds' wire words** (`acquired`, `lost`, `locked`, `lock_lost`, `hit`, `miss`, `kill`, `struck`, `section_lost`, `target_section_lost`, `power_online`, `destroyed`, `disabled`, …; `NoticeKind::as_str`), which already fit OSC 440's `[A-Za-z0-9_-]{1,64}`, plus `overheat`, the frame's own `heat.overheated`. The row's examples (`contact-gained`, `contact-lost`) were names before the kinds were read; the acceptance says "the sound names are the notice kinds", and that wins. The pack (G.11) names its files by these words.
- **BEL only for the kinds a pilot must hear** (`BELL_KINDS`: `acquired`, `lock_lost`, `struck`, `section_lost`, `kill`, `power_online`, `destroyed`, `disabled`, `overheat`), and at most one bell every two seconds whatever the kind: one bell for every notice of a firefight would be a buzz.
- **Kitty gets BEL, not OSC 99.** Kitty's OSC 99 is its desktop-notification protocol, and its `s=` sound plays with a notification: one popup a contact. The row asked for it before that was weighed; a kitty with sounds by name is a later cut if kitty grows a sound-only form.
- **On by default**, per connection: `@sounds on|off` (transport-side, as `@pixel/encoder`, kept across `@notui`).
- **The TUI only.** The line client has no probe and so no terminal name; it would get BEL alone, and the line client prints the notices already. Left for a cut that asks for it.

What was built:

- **`tui::sound`**: `Sounds` takes each seated `arena.cockpit` frame (a frame's notices are its own pulse's; a read verb's re-emitted frame carries none, so nothing sounds twice) and queues, per kind and at most once a `DEBOUNCE` (2 s), w11term's `ESC ] 440 ; 1 ; play ; <name> ESC \` or a BEL; a name that is not one (`valid_name`: 1–64 of `[A-Za-z0-9_-]`, never `system` or `off`) is never sent. The bytes ride the next paint, after the frame. The overheat alarm is `overheat` on every frame that still says `overheated`, so it repeats on the debounce while it lasts and stops with the frame that clears it.
- **The probe asks `XTVERSION`** (`CSI > 0 q`, before DA1, which stays last), and **the key parser swallows DCS** (`ESC P … ESC \`, or BEL-ended) as it swallows APC: `>|<name version>` decodes as `Key::TermVersion` (printable ASCII, cut to 48 bytes, inline so a `Key` stays `Copy`), any other DCS vanishes, and a burst that ends on `ESC P` is still Alt-P (D-21-24: the reply used to decode as F1 plus typed text). `names_w11term` reads the first word, case-folded.

## G.11

The asset pack over the player's own connection, to w11term's `docs/game-client-protocol.md`. Rulings taken here (each cheap to unwind):

- **Compiled in, not deployed beside.** The row asked for "a shipped `assets/` directory" and "deploy.sh shipping `assets/`". The pack is the repository's `assets/`, but `mush_net_ssh::assets::SHIPPED` compiles every file into the binary (`include_bytes!`, the unit looks' idiom), and a test holds the table to the directory file for file. So the pack ships atomically with the gateway that serves it (the protocol's "ship the manifest and assets atomically with deployment"), nothing on the box can add a file to it, no `[assets]` config and no deploy-script change are needed, and a request never names a path on the box: the tree is answered from memory. The cost: a new pack needs a gateway restart (`GATEWAY_RESTART=1`), which is also the moment every w11term reconnects and is told the new version.
- **Placeholder sounds.** Nothing was ever recorded, so the first pack is nineteen short synthesised tones (`assets/sounds/<kind>.wav`, 16-bit mono 22.05 kHz, 268 KB in all), one a notice kind G.10 sounds and `overheat`, distinct enough to tell apart and meant to be replaced: drop a real WAV in under the same name and run `ASSETS_BLESS=1 cargo test -p mush-net-ssh --lib assets::tests::bless` to write the manifest again (`ASSETS_TONES=1` makes the tones again). The pack version is `pack_` and 16 hex digits of the names' and hashes' SHA-256, so it changes exactly when the pack does.
- **Only in game, one a connection.** The SSH server takes a second session channel only once the connection is in game (the `connected` flag a character sets) and only while the pack is served, holds it until it asks for a subsystem, and serves `sftp` and nothing else on it; a third channel, a second `sftp`, a shell or exec on it, and `sftp` on the game's own channel are refused. w11term opens it only after the TUI's `pack` announcement, which is sent in game.
- **The web Hello's `asset_pack` is left out**: the web client has no use for the pack yet (its sounds and sprites are its own); the field is a one-line addition when it does.

What was built:

- **`mush_net_ssh::assets`**: `AssetPack::from_files` checks a pack against w11term's rules — the manifest an object of exactly `version` (1), `pack_version` and `files`; each entry exactly `name`, `path`, `kind`, `sha256`, `size`; names and the version OSC 440 tokens and never a DOS device name; names and paths unique; a sound never `system` or `off` and always `.wav`; paths of two or more plain segments, no `.` or `..`, at most 200 bytes; every size the file's and nonzero, every hash the file's; at most 256 files, 8 MiB a file, 64 MiB a pack, 256 KiB of manifest; and nothing shipped that the manifest does not list. `AssetPack::shipped` checks the compiled pack once and serves nothing (logged once) if it fails.
- **`AssetsSftp`** (`russh_sftp::server::Handler`, protocol v3, no extensions advertised): `/`, `/assets`, the pack's directories and files; `realpath` (a relative path is from `/assets`, so `.` is the pack's root), `stat`/`lstat`/`fstat` (directories 0555, files 0444), `open` for read alone, `read` (at most 64 KiB, `Eof` past the end, paced to 1 MiB a second a session), `close`, `opendir`/`readdir` (sorted, then `Eof`); everything else, and any path that climbs, is `PermissionDenied`; 32 handles at most. `EndOnError` wraps the channel's stream so a read error ends the session (the crate's loop would otherwise retry a failing read for ever).
- **The announcement** (`tui::sound`): a w11term is sent `ESC ] 440 ; 1 ; pack ; <pack_version> ESC \` when its `XTVERSION` names it and again every ten minutes (`REANNOUNCE`, through the TUI's heal tick), never with a frame; a plain terminal never.
- **The dependency**: `russh-sftp` 3.0.1 (the version w11term's client uses), and `sha2` for the checks.

**Verified.** `mush-net-ssh`: the shipped table is the directory and passes, the manifest is the blesser's, every sound G.10 rings a bell for has a file, every WAV a RIFF/WAVE PCM file with the exact RIFF length and under five seconds; a pack with a wrong hash, a wrong size, a one-segment path, a climbing path, a reserved name, a device name, a file not shipped, an unknown field or a stray file is refused; paths normalise and never climb; over an in-memory pipe to russh-sftp's own client, the manifest and every file read back byte-exact with the manifest's sizes and hashes, the tree lists, and a write, a create, a rename, a remove, a mkdir and two climbs are refused; **over a real SSH loopback**, a player in game opens a second channel, asks for `sftp` and reads the manifest the gateway ships (its version the announced one), a write is refused, a third channel is refused and the game's own channel still answers, while a connection at the welcome screen is refused the second channel; the announcement (at once, not again within ten minutes, again after; never to a plain terminal; never a bad version). Not smoked with w11term itself yet: that is the dev2 smoke, w11term's `assets-ready` event the proof.
