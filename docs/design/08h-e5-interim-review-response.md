## 1. Findings — verdicts and decisions

### F1 — cross-record invariants at boot. **TRUE.**

Boot validates one document at a time. `crates/mush-housing/src/boot.rs:86-158` is a flat loop; `property:`/`tenancy:` parse through the `TryFrom` wires (`record.rs:156-158`, `300-359`; `802-804`, `979-1040`), which check anchor ∈ rooms, feature caps, guests ≤ 16, history ≤ 32, plans ≤ 8, sources ≤ 8, tenants non-empty and ≤ 8 — nothing a wire can see beyond its own record. The reconcile passes 1–7 (`boot.rs:183-523`) check room liveness, dead tenants, orphan obligations/contracts, cadences, scenes, and the Let latch; none checks room overlap, a second live tenancy, or that `t.property` exists. `property_of_room` is `self.properties.values().find(..)` — first match in a `BTreeMap`, lowest id (`module.rs:286-288`); `may_reach` returns `Access::Staff` (admit) when that property has no live tenancy (`hooks.rs:129-134`), so the reviewer's overlap scenario fails open exactly as described. `live_tenancy_of` filters all tenancies, takes the first, logs `tracing::error!` if a second exists, and returns the lowest id (`module.rs:258-273`). A tenancy on a missing property loads silently; the tick then assesses it at tier 0 via `unwrap_or_default()` (`tick.rs:241-246`). The write paths refuse both conditions (`commands.rs:596-606`, `925-936`; tests `property_rooms_refuses_a_room_another_property_already_holds`, `a_second_live_tenancy_on_one_property_is_refused` in `tests/e5b.rs:652`, `:844`); no test loads the corrupt shapes at boot.

**D-LBK-1 — container invariants are validated at boot, and a violation fails closed; it is never process-fatal.** A new reconcile pass 0 runs before any derived index is built and before passes 1–7. It checks (a) one property per room, (b) at most one live tenancy per property, (c) every live tenancy names a loaded property. A violation puts every record involved into an in-memory **quarantine set** (rebuilt each boot, never persisted) with these effects: every room of every property involved renders `may_reach = Refused` for everyone but staff, and `HousingDestroyGate` refuses their destruction; the assessment tick skips quarantined tenancies (no assessment, no window advances, nothing pages the tenant); members see the tenancy as "(under review)" in `+home`/`@tenancy/show`, everyone else gets the hidden text; exact-mode rent periods that fall inside the quarantine are forgiven with `ForgiveCause::Suspension` (the E4b1 seam) so nobody pays for a home we refused them — if no callable seam exists for that, the fold records the deviation and pages instead; one escalation per conflict, subject `housing.corrupt:<kind>:<ids>` (the ladder's dedupe/reopen rules), carrying the resolving command filled in (`@property/rooms <id>=remove <room>`, `@tenancy/end <id>=…`, or `@housing/quarantine release <key>` after a manual repair); `@housing/quarantine show` lists the set. Money on the economy side keeps its own strict boot gate (E2): the ledger halts on corruption because money is at stake; the world does not halt on a housing document.

Why not boot-fatal: the staff-scarce principle. One corrupt document must not take the whole world down and park every player on "wait for staff"; the fail-closed quarantine gives the same safety (nobody enters an occupied home they should not) while everything else runs, and the page carries the exact repair. Owner: housing. Effort M. **Fix-before-E6/E7** — the fail-open path exists today regardless of E6.

### F2 — tick budgets bound work, not scanning. **TRUE**, with two precision notes.

Housing's tick (`tick.rs:55-88`) materializes the **open** index (`boot.rs:539-541`, `module.rs:175`, `215-217`) — every non-ended tenancy, not the whole population — rotates it (`63-65`), and `MAX_ASSESSMENTS_PER_FIRE = 128` (`module.rs:65`) counts only `Worked` (`70-79`); `last` is set only on `Worked`, so an all-skipped fire scans everything and leaves the cursor where it was (`83-87`). Worse, `step` clones the full `Tenancy` (`tick.rs:121`, `flow.rs:588-590`) **before** the `now <= state.position` due check (`141`). The WoD tick (`evaluate.rs:68-114`) has the same rotation and cursor rule with `MAX_EVALUATIONS_PER_FIRE = 128` (`store.rs:46`); its `step` at least returns before cloning when not due (`123-130`).

**D-LBK-2 — two budgets, a cursor that advances past what it visited, and a short-circuit between periods.** `MAX_VISITED_PER_FIRE = 256` and `MAX_WORKED_PER_FIRE = 128`, both enforced independently in both tickers (the reviewer's defaults, accepted). The cursor advances past the last **visited** id, skipped ones included, so rotation is fair and every fire's scan is bounded. The due check reads the small state document before anything is cloned. Both tickers record the cadence position they last swept completely; while that position is unchanged and the last full sweep found nothing due, a fire visits nothing — a membership change (a new tenancy or profile, a cadence advance) clears the short-circuit. Between period boundaries the tick then costs O(1); at a boundary the worked budget spreads the population over fires as today. Owner: housing + ruleset-wod. Effort S. **Fix-before-E6/E7** — the as-built docs claim "bounded per fire", and the claim must be true.

### F3 — persisted WoD profiles and notices bypass their bounds. **TRUE.**

Only `Property` and `Tenancy` have validating wires. `SpendingProfile` is a plain `#[derive(Deserialize)]` with `#[serde(default)]` fields (`ruleset-wod/src/economy/record.rs:503-557`), as are `CareerProfile` (`190`), `HavenQualities` (`317`), `PromptOption` (`433`), `Prompt` (`444`), `ProfileEvent` (`494`); the loader enforces parse and `p.obj == key` only (`store.rs:294-327`). The documented caps — `MAX_PROFILE_HISTORY = 32`, `MAX_SOURCES = 8`, `MAX_TEXT_BYTES = 64`, options ≤ 4, qualities ≤ 8, history line ≤ 256 — are enforced at write time only (`commands.rs:300-302`, `record.rs:611-617`, `227`, `330-338`, `prompt.rs:245-319`). `+prompt` renders every persisted option (`commands.rs:372-374`); `+career` every source and quality (`167-176`). Housing's `PendingNotice` (`module.rs:147-153`) is capped at 32 per character on load (`boot.rs:139-150`) but its text is clamped to 240 bytes only on the write path (`notice.rs:35`, `46`, `99-108`).

**D-LBK-3 — the E5a fold rule applies to every E5 persisted type.** `SpendingProfile` and its nested types get a `TryFrom` wire that runs the constructor invariants and every documented cap; an invalid profile follows the existing policy — skipped loudly and re-derived in the same boot (`store.rs:319-327`, `boot.rs:91-136`). `PendingNotice` gets the 240-byte cap on load; an oversized notice is dropped (notices are ephemeral). Tests: an oversized payload refuses to load; a five-option prompt refuses; `+prompt` can never render more than four options. Owner: ruleset-wod (+ housing for the notice). Effort S. **Fix-before-E6/E7.**

### F4 — hot reads are global scans. **TRUE.**

`may_reach` (`hooks.rs:127-147`) calls `property_of_room` (linear over properties) and `live_tenancy_of` (linear over **all** tenancies, ended included — not the open index); `move_attempt` calls it up to twice (`hooks.rs:72`, `93-97`), `carry_attempt` twice (`111-115`); `has_live_tenancy` and `live_tenancies_of_tenant` are full scans (`278-280`, `291-293`). The only index is `open` (`module.rs:175`), used by the tick alone. `open_ops_for` rebuilds the full per-faction map over every profile on every call (`store.rs:158-166`, `record.rs:642-650`); its sole runtime caller is `prompt::offer` (`prompt.rs:130-133`), reached at most once per worked step — the reviewer's "once per evaluated profile" is the exact upper bound.

**D-LBK-4 — derived indexes are explicitly non-authoritative projections.** They are rebuilt at boot after pass 0 (D-LBK-1), maintained by the module's single write path, never persisted, and need no verb. Two ship with D-LBK-1 because pass 0 produces them: room → property and property → live tenancy | conflict (which also removes the ended-tenancy scan from `may_reach`). Tenant/guest → tenancy ids and faction → open-prompt count follow. Owner: housing + ruleset-wod. Effort M. The first two **fix-before** (with D-LBK-1); the second two **fix-during-E6**.

### F5 — list output capped after unbounded collection. **TRUE.**

`LIST_CAP = 20` (`commands.rs:52`); `emit_list` truncates after collection (`382-394`); `property_list` (`850-876`) and `tenancy_list` (`1279-1307`) filter and format every visible record first. `+home` clones and renders every live tenancy of the actor (`1450-1483`); the A6-fold ambiguity refusal lists all of them (`1517-1528`). There is no per-character residence cap; `MAX_TENANTS = 8` bounds the other direction.

**D-LBK-5 — no gameplay cap on residences; cursor pagination.** Agreed with the reviewer: a character may hold any number of tenancies. `@property/list` and `@tenancy/list` take `after=<id>` and collect at most `LIST_CAP + 1` records from the ordered map before rendering; `+home` and the ambiguity refusal read the tenant index (D-LBK-4) and page the same way. Owner: housing. Effort S. **Fix-during-E6.**

## 2. Answers to the six questions

**Q1 — are overlapping rooms, missing property references, and multiple live tenancies boot-fatal container corruption?** They are container corruption and they must be caught at boot, never fail open — agreed. They are not process-fatal: D-LBK-1 quarantines the records involved (fail closed, staff-only access, tick frozen, rent forgiven, one page per conflict with the repair filled in). The process refuses to boot only for the ledger (E2's strict durable gate), where a wrong answer moves money.

**Q2 — visited/worked tick budgets?** 256 visited / 128 worked, both enforced independently, cursor past the last visited record, plus the between-periods short-circuit (D-LBK-2).

**Q3 — derived indexes as rebuildable projections?** Yes, on three conditions: rebuilt at boot only after the container invariants pass; written only from the module's single write path; never persisted and never treated as authority — a projection that disagrees with the records is a bug in the writer, not a state to repair (D-LBK-4).

**Q4 — narrow the programmatic jobs API from `set_job_status`?** Yes. `mush_jobs::set_job_status` is `pub`, takes any `JobStatus`, and runs no payload handlers (`crates/mush-jobs/src/api.rs:245-284`); housing is its only caller (`mush-housing/src/flow.rs:377-386`, `419-421`, both `Resolved`, `by = GOD`), and no narrower terminal op exists (`api.rs:76-267`). That surface lets a module flip a payload-bearing job to `Resolved` without applying its payload — the exact class E4c closed when it made `jobs.resolved` a fact only from the applied-payload marker. **D-LBK-6:** `set_job_status` leaves the public API; `resolve_plain_job(ctx, id, by, note)` and `deny_plain_job(..)` replace it, refuse a job that carries a payload, refuse a non-terminal target, and are the only external terminal path; `+job/approve|deny` keep the internal path where payload handlers run. Housing's two callers switch. Owner: jobs (E side). Effort S. **Fix-before-E6/E7.**

**Q5 — which E5 records migrate first to K typed state?** Agreed: property and tenancy before profiles, because they carry physical-access and destruction authority and they have no journal companion. Today no E5 record touches `ActionStateStore` or a `StateFamilyHandle` (grep in both crates: zero); every E5 doc is a plain `ModuleWrite::JsonSet` through `Outbox::defer` (`housing module.rs:316-318`; `wod store.rs:190-192`; cadence `economy api.rs:1447-1453`), which `08d` records as deliberate (deviations 10, 11, 14). The order is property/tenancy → cadence (with Q6) → profiles → obligations/contracts, and the gates from `08c` §12 apply piecewise: property/tenancy need gate (1) mixed write sets — ending a tenancy writes tenancy + assess + notice in one bundle — and gate (2) `Ctx` typed-family reads outside an action, because boot reconciliation, the tick, and the movement hooks all read them there; not gate (3), no ledger append. Obligations and contracts need all three. Each migration is an explicit owner decision recorded in the owning plan (`08c` §12's rule: the document stops being sole authority), never a side effect of a K merge. E7 cut 10 already gates on K6 for this reason.

**Q6 — is cadence `revision` a clock generation?** No, agreed. `CadenceClock.revision` is a staleness stamp (`mush-economy/src/clock.rs:247-248`): 1 at create, bumped on every advance (`clock.rs:293`, `303`), read only by `@econ/cadence show`, never compared or carried — `EconomicClock::Cadence(id)` holds the id alone and resolves to `position` (`clock.rs:62-72`, `342-345`); housing reads `position` only (`module.rs:421-425`). K4a's `generation` changes when a clock is re-anchored or re-rated (`mush-core/src/clock.rs:64-103`, `105-127`), and `ClockStamp::checked_cmp` refuses cross-identity comparison; there is no bridge between the two today (`ClockRef::Registered` appears in no crate outside core; E5c's stamps on prompts are informational). **D-LBK-7:** `CadenceClock` gains `generation` (serde default 1; bumps only on a repoint, and no verb repoints today, so it stays 1) and `schema` (serde default 1) so existing documents load unchanged; `revision` stays the staleness stamp. At convergence, after K6, a migration verb (`@econ/cadence register`, or a boot pass under a config flag) stamps `schema = 2` and registers each cadence as `Registered { owner: economy, id: cadence.<name>, generation }` — the `08c` §12 adapter row as written; the journal is untouched (the serde shape stays). Until then cadences remain adapters, and anything that needs the world timeline reads it through K4a's `Ctx::world_ic_now`, not through a cadence. Owner: economy. Timing: at convergence, not before.
